## 6. 한계와 주의

1. **낙관적 점수:** 같은 17건을 개발 중 여러 번 돌려 프롬프트와 도구를 다듬은 뒤의 값이다. 새 질문에 대한 성능이 아니다.
2. **개선이 한꺼번에 들어갔다:** 프롬프트 두 건, 마스킹 수정, 계정 교체가 함께 적용되어 전체 17/17 의 원인을 나눌 수 없다. 원인이 분리된 것은 4절에서 "통제 실험"으로 표시한 두 건뿐이다.
3. **재현성은 두 번만 확인했다:** 중간 점검(6fix)과 정식 2차가 모두 17/17 이고 고쳐진 건도 같다([8, 10]). 그러나 이는 두 번의 단일 실행일 뿐이며, 에이전트는 같은 질문에도 호출 경로가 달라질 수 있다. (#10 은 보완 후에도 한 번 실패한 적이 있다)
4. **표본 크기:** 케이스 17건에서 1건이 약 6%p 다. negative 는 3건이라 1건 차이로 33% ↔ 67% 가 갈린다. RAGAS 는 8케이스 평균이다.
5. **judge 편향 가능성:** judge 가 에이전트와 같은 모델이다. 규칙 판정 6건(guardrail·HITL 포함)은 영향이 없고 LLM 판정 11건에만 해당한다. 판정 사유는 `round2.json` 의 `detail` 에 남아 있다.
6. **기준의 민감도:** 충족률 70% 는 특성이 2~3개인 케이스에서 사실상 "전부 충족"을 요구한다. 1차의 #8·#10 이 이 때문에 탈락했다.
7. **judge 는 근거 위치를 검증하지 않는다:** 케이스 2 처럼 답변이 맞아도 설정 파일을 직접 확인했는지는 위치 지표로만 드러난다.
8. **토큰 비용:** 입력 토큰이 38% 늘었다. 정확도 개선의 비용이다.

## 7. 남은 과제

- **케이스 12 의 RAGAS precision:** `search_code` 가 먼저 호출되어 무관한 청크가 컨텍스트 앞에 쌓인다. 검색 `top_k` 또는 도구 호출 순서를 손볼 여지가 있다.
- **케이스 3 의 faithfulness 변동:** 답변이 컨텍스트에 없는 부연을 덧붙이는지 주장별로 확인하지 못했다. RAGAS 결과에 주장별 판정이 남지 않는다.
- **`build_dependency_graph` 단독 답변:** 이 도구는 위치를 반환하지 않아 위치 지표에 잡히지 않는다.
- **평가 확장:** 케이스 수 확대, 서로 다른 계열의 judge 로 교차 확인, 새 질문(개발에 쓰지 않은 질문)으로 일반화 점검.
- **운영:** 체크포인터가 메모리 기반이라 서버 재시작 시 승인 대기가 사라지며, LangFuse 는 적용하지 못하고 JSON 로그만 쓴다.
