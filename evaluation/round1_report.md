## 4. 실패 건 분석

### #8 결제 모듈은 어떻게 동작해? (negative, 충족 1/2)
- **증상:** "결제 모듈이 존재하지 않습니다" 를 두 번의 검색 근거와 함께 정확히 안내했고 가상 클래스도 지어내지 않았다. 빠진 것은 기대 특성 2 — "유사한 기능이 있다면 방문(Visit) 등록 정도로 제한적으로 제안". 답은 대신 일반 기능 표와 후속 질문 제안(도표·기능 목록)만 했다.
- **원인 분류:** 프롬프트. 시스템 프롬프트에 "없는 것을 물으면 찾을 수 없다고 답한다" 만 있고 "가장 가까운 실제 기능을 제안한다" 는 지시가 없다.
- **판정 주의:** 기대 특성 2 는 "있다면"이 붙은 조건부 항목이라 judge 해석에 따라 갈릴 수 있다. 특성이 2개뿐이라 하나를 놓치면 50% 로 탈락한다. (기준 70% 에서는 2개짜리 케이스가 사실상 전부 충족이어야 통과)
- **개선안 후보 (7-4):** 프롬프트에 "소스에 없는 기능을 물으면 없음을 밝힌 뒤, 가장 가까운 실제 기능을 근거(파일:라인)와 함께 한 줄로 제안한다" 를 추가.

### #10 `OwnerService` 의 `deleteOwner` 메서드는 뭘 해? (negative, 충족 2/3)
- **증상:** `OwnerService` 와 `deleteOwner` 가 없다는 것, 서비스 계층이 `ClinicService` 하나이고 삭제 기능이 없다는 것은 정확히 답했다. 기대 특성 3 — "`ClinicService` 가 제공하는 메서드(9개) 안내" — 에서 `findOwnerById`, `saveOwner` 2개만 제시했다.
- **실제 결함:** 질문이 Owner 관련이라 Owner 메서드만 추렸다고 해도 `findOwnerByLastName` 이 빠졌다. 즉 도구 결과(`list_structure`)에 있는 항목을 요약 과정에서 누락한 **완전성 문제**다.
- **원인 분류:** 프롬프트 (요약 범위 지침 부재). 검색·도구 문제는 아니다. 도구는 전체 메서드를 반환했다.
- **개선안 후보 (7-4):** "존재하지 않는 항목을 물었을 때는 해당 서비스 계층의 실제 메서드 목록을 `list_structure` 결과 그대로 빠짐없이 안내한다" 를 추가.

### 통과했지만 약점이 보인 건
- **#6 (75%):** 캐시 매니저 설정(`tools-config.xml`)을 `search_code` 두 번으로 찾지 못하고 `read_file` 로 설정 파일을 확인하지 않았다. 통과 기준 70% 를 간신히 넘었다. 질문이 "캐시가 적용돼 있어?" 일 때 캐시 설정 파일까지 확인하는 흐름이 없다.
- **#12:** `read_file` 을 7번 호출했다. 정확하지만 비효율적이다. (지연 17초)

**해석**
- **목표를 두 가지 모두 넘었다.** 다만 8건 평균이고 채점 LLM 의 노이즈가 있어 근거 recall(5-1절 80%)과 함께 "목표 근처 이상" 정도로 읽는 것이 안전하다.

- **케이스 3 (기본 프로필)의 faithfulness 0.65** 는 답변이 컨텍스트에 없는 부연(변경 방법 설명 등)을 덧붙인 결과로 보이나, RAGAS 결과에는 주장별 판정이 남지 않아 확인하지 못했다. 필요하면 7-4 에서 `--reuse` 로 샘플을 재사용해 원인을 본다.
- **answer_relevancy 0.53 은 답변 품질이 낮다는 뜻이 아니다.** 이 지표는 답변에서 역으로 질문을 생성해 원래 질문과 임베딩 유사도를 비교한다. 답이 길고 부연이 많은 한국어 답변에서 낮게 나오는 경향이 있고, SERVICE.md 에도 목표가 없다. 개선 전후 비교용 참고값으로만 쓴다.
- **precision 이 낮은 케이스(1·4·12)** 는 `search_code` 가 상위 5건을 돌려주는 구조 때문이다. 정답이 일부만 포함된 청크가 섞여 들어온다.

## 6. 한계와 주의

1. **낙관적 점수:** 평가 전 같은 케이스로 반복 개발했다. 88% 는 일반화 성능이 아니라 "이 17건에 맞춰 다듬어진 상태" 의 값이다.
2. **표본 크기:** 17건이라 1건이 약 6%p 다. negative 는 3건이라 1건 차이로 33% ↔ 67% 가 바뀐다.
3. **judge 편향 가능성:** 에이전트와 judge 가 같은 모델이다. 다만 이번 실행에서 judge 는 자기 모델의 답 2건을 근거를 대며 실패 처리했고, 100% 목표인 guardrail·HITL 은 규칙 판정이라 영향이 없다. LLM 판정 11건에만 해당한다.
4. **기준 민감도:** 충족률 70% 는 특성이 2~3개인 케이스에서 사실상 "전부 충족" 을 요구한다. (#8: 1/2, #10: 2/3 가 모두 탈락) 기준을 66% 로 낮추면 #10 만 통과한다.
5. **RAGAS 는 정답을 아는 8케이스만 측정했다(5-2절).** negative·guardrail·도표·개요 케이스에는 reference 가 없어 검색 정확도·충실도를 재지 못한다. 채점 LLM(Haiku)의 노이즈와 케이스 수(n=8) 때문에 소수점 둘째 자리 차이는 의미가 없다.
6-1. **`contexts` 파싱 버그(1차 측정에 미친 영향):** 1차 이후에 마스킹 정규식이 JSON 이스케이프를 깨뜨려 `datasource-config.xml` 청크가 들어간 검색 결과의 `doc_id` 파싱이 실패하는 버그를 찾아 고쳤다. 1차 RAGAS 샘플에서는 케이스 3 의 컨텍스트 1건만 영향을 받았다. 에이전트 답변과 판정(15/17)에는 영향이 없다. 이 리포트의 1차 수치는 수정 전 그대로 두고, 수정 후 값은 README 의 "케이스 6 개선 후 재측정"에 따로 적었다.
7. **영향도 정답 목록 변경(재채점):** 1차 실행 당시 정답 목록은 CSV 의 8개였는데, 소스를 grep 해 보니 `JdbcOwnerRepositoryImpl.java:108`, `JdbcVisitRepositoryImpl.java:81` 도 `birth_date` 를 SELECT 로 읽는 실제 영향 대상이었다. 정답 목록이 불완전하면 누락을 못 잡아 재현율이 부풀려지므로 10개로 넓히고, 부분 문자열 매칭(`Pet.java` 가 `JdbcPet.java` 에도 잡히는 오탐)을 단어 경계 매칭으로 바꿨다. 저장된 1차 답변으로 다시 채점한 결과는 10/10 으로 변하지 않았고 오탐으로 부풀려진 흔적도 없었다. 2차도 같은 정의로 측정한다. 단 정답 목록에 없는 실제 영향 파일은 여전히 잡지 못하므로 소스가 바뀌면 목록부터 다시 확인해야 한다.
